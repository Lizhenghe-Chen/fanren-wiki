## 1. 一次性把评论抓全

- **视频维度的 oid**：页面里 `<bili-comments data-params="1,117414977079767">` 的**第二段**就是 aid（= API 的 `oid`），`type=1`。别拿 BV 号去试。
- **在“已经在看这个视频”的页面上下文里取**（登录态、访客 cookie 都现成，别用 curl 另起会话）：
  - 主楼：`GET https://api.bilibili.com/x/v2/reply?type=1&oid=<OID>&pn=<页码>&ps=20&sort=2&nohot=1`
    `sort=2` 是按时间（`sort=0` 是热度）；翻到**返回条数 < 20** 为止。
  - 楼中楼：`GET https://api.bilibili.com/x/v2/reply/reply?type=1&oid=<OID>&root=<主楼 rpid>&pn=1&ps=20&nohot=1`
    （对每个 `rcount > 0` 的主楼拉一遍，页数同样看返回条数）
- **判定“抓全了没”**：`主楼条数 + 楼中楼条数 == data.page.count`（本次 59 + 42 = 101 ✓）。总数对得上就不用再翻页。
- 有用字段：`rpid`(主键) / `root` / `parent` / `member.uname` / `content.message` / `like` / `ctime` / `rcount` / `reply_control.location`。

## 2. 数据怎么“带出来”（关键技巧）

- 现在这代工具会把过长输出截断/落盘，**别指望一次性把整份评论 JSON 当返回值带回来**。
- 稳妥做法：本机起一个 127.0.0.1 的小收集器（带 CORS + 处理 OPTIONS），页面里
  `fetch('http://127.0.0.1:<PORT>/save', {method:'POST', body: JSON.stringify(payload)})` 把整份数据 POST 出来落盘。
  `http://127.0.0.1` 属于“可信来源”，https 页面里不会被当混合内容拦掉。
- 落盘后**分段**打印（20~40 条一次）：整行太长照样会被截断；`grep` / `view_range` 配合看。
  （同理：工具返回的临时文件路径不一定能从 shell 里读到，别依赖它。）

## 3. 读评论：一次读全 + 先分类

一次读全，不要抽样；然后按主题归类，再决定动不动手：

| 类别 | 例子 | 处理方式 |
|---|---|---|
| ① 事实/方位纠错 | “出生点跑正道盟了”“大晋太小” | 能落到数据/代码的 → 改 |
| ② 完整性 | “为什么不把图放完整”“太素、没标山川” | 看是不是设计取舍 → 改口径或补图 |
| ③ 定位与预期 | “这不是地图”“标题误导新人” | **用口径解决**：页脚/考据注明“同人示意、非官方、非等比” |
| ④ 可用性/性能 | 打不开、卡、加载慢 | 能优化的优化（如下线未引用的大图），不能的直说（GitHub Pages 网络） |
| ⑤ 站点体验 | 关系图乱、找不到入口 | 记下来，评估后改 |
| ⑥ 需求 | 做成放置游戏、也做个蛊真人 | 礼貌回应，不承诺排期 |
| ⑦ 纯情绪/点赞 | “全是乱的”“只能给 7 分” | 不逐条回，最多一条邀请具体化 |

## 4. 先查 git，再改（省掉一半工作量）

- 同一批反馈里常有**已经修过**的：`git log --oneline -25 -- public/index.html`，再 `git show --stat <sha>` 看提交说明里有没有“已按官方图重排 / 已撤图 / 已挪位置”。
- 判断顺序：**已修 → 只回复；没修但可改 → 改 + 跑验收 + 部署；不可改 → 写清楚口径**。
- **不要盲从评论者**：互相矛盾的说法很常见（同一张图有人说“乱星海在北”、有人说“该在左边”）。一律回到原著原文 / 官方动画图；站上已经有「地理考据」抽屉的，直接引用自己已有的考据，比临时考据可靠。
- 属于“表达形式”而不是“错误”的（比例、画风、密度），宁可写口径也不硬改布局——改布局会牵动天南贴图、乱星海群岛、巡游路径这一整串联动物。

## 5. 在评论区回复（API 实操）

- 前置：在**已登录**的该视频页面上下文里发请求；`csrf` 取 cookie 里的 `bili_jct`。
- 接口：`POST https://api.bilibili.com/x/v2/reply/add`（`Content-Type: application/x-www-form-urlencoded`）
  - 字段：`oid` `type=1` `message` `csrf` `plat=1` `root` `parent`
  - **回复主楼**：`root = parent = <主楼 rpid>`
  - **回复楼中楼**：`root = <线程主楼 rpid>`、`parent = <被回复者 rpid>`
  - ⚠️ **最大的坑：`parent=0` 会返回 `code:0`（看着成功）但根本不落楼** —— 线程列表里查不到。必须 `parent=root`。本次有 16 条因此白跑，重发才对上。
- 节奏与复核：每条间隔 **8~9 秒**（防风控）；发完用
  `reply/reply?type=1&oid=<OID>&root=<主楼 rpid>&pn=1&ps=20` 回查该楼里有没有自己的回复（按 `member.uname` 匹配）——**确认可见再发下一条**。
- 文案口径模板（短、只讲事实、不辩论）：
  - 已修：`已按动画官方天南图重排：…，网页版已更新（视频不重做）`
  - 做不到：`原著是大晋十倍于天南；图上面积是示意（非等比），已在页脚和「地理考据」写明口径`
  - 只是理解差异：`原著里乱星海在天南之北、无边海之外（自阴冥之地脱身是“南飞万里”回天南），口径写在顶栏「地理考据」里`
- 纪律：不删不改别人的评论；**同一楼只回一条**；不为情绪评论逐条回怼。

## 6. 常踩的坑清单

1. **`bili-comments` 是 web component + lazy 加载**：`textContent` / `innerText` **穿不过嵌套 shadow root**（外层 host 的 textContent 只有几百字节）。要么递归 walk `node.shadowRoot`，要么直接用上面的 API——API 更省事也更准。
2. **页面在后台标签时 `requestAnimationFrame` 被节流**：画布会停在旧帧，浏览器工具截出来的图可能是几分钟前的画面。要看页面真实样子，自己用 CDP headless 跑（`Emulation.setDeviceMetricsOverride` 定视口 + `Page.captureScreenshot`），**别用内置浏览器截图当证据**。
3. 自定义画布地图的相机语义：`zoom` 就是「屏幕像素 / 世界单位」；`WORLD` 是 3000×3450，人界带在 `y≈2200~3400`。定位一处先 `snapView(x,y,z)` 再 `state()` 读可见点位，别靠猜。
4. 抓取/回复脚本里**不要**把 cookie、csrf、评论原文写进仓库；临时脚本跑完就删。
5. 工具输出被截断时，落盘的临时文件**不一定能从 shell 读到**；优先在页面里就把结果算小（只回传命中项、计数、抽样）。

## 7. 一次完整回合的时序（照抄即可）

1. 抓全评论（§1）→ 落盘（§2）→ 通读 + 分类（§3）
2. `git log` / `git show` 对照，标出「已修 / 待改 / 只回口径」（§4）
3. 待改的改完 → `node dev/tools/verify.mjs` 全绿 → commit + push → `curl` 线上复核新文案
4. **确认线上已生效之后**再回复（回复里写了“网页版已更新”就必须是真的）
5. 逐楼回查可见性（§5）→ 收尾：删临时脚本、清临时文件
